## 라운드 1 — 데이터 모델 뼈대 (2026-07-23)

### D1. 지도(Map)와 바운더리(Boundary)의 관계
**결정: 단일 지도 + 다중 바운더리 오버레이**

- 지도는 사용자당 하나(내 전체 지도)이고, 바운더리는 그 위에 켜고 끄는 반경 레이어.
- 모든 장소가 한 지도에 모이고, 선택된 바운더리·테마·상태로 필터링해서 본다.
- **근거**: 1차 설계서 4.4("현재 선택된 폴더·태그에 해당하는 장소 표시")와 13.2 메인 지도가
  "하나의 지도에서 필터링"하는 그림에 가깝다. 한 장소가 여러 바운더리에 동시에 속할 수 있다는
  4.3 조건도 자연스럽게 만족한다. 프로토타입도 이미 이 구조(집/직장 전환 + 반경 필터).

### D2. 장소(Place) vs 활동/프로그램(Program)
**결정: MVP는 Place 단일 엔터티. 활동 정보는 주제별 구조화 메모로.**

- 활동(클래스명·가격·일정)은 그 장소에 연결된 `Note`(topic 필드)로 관리.
- **근거**: 초기 복잡도를 낮춘다. `Note.topic`(가격/일정/후기)이 이미 있어 활동 정보를 담기 충분.
  활동검색 에이전트 연계(3단계)에서 Program 분리를 재검토한다.

### D3. 다른 사용자와 공유/협업
**결정: 완전 개인용. 공유·공동편집·공개지도 MVP 제외.**

- **근거**: 1차 설계서 14장에서 "사용자 간 공동 편집"·"공개 지도 마켓"을 이미 제외로 명시.
  인증·권한 모델이 단순해진다. 읽기전용 공유 링크는 5단계 이후 검토.

### D4. 추천 실행 시점
**결정: 온디맨드. 사용자가 요청할 때만 AI 검색 실행.**

- **근거**: "승인 중심" 철학과 일치하고 비용·복잡도가 낮다. 정기 자동 탐색은 백그라운드 작업
  큐·알림 정책과 묶여 있어 이후 확장으로 미룬다.

## 라운드 2 — 프로토타입 조율 (2026-07-23)

프로토타입(`app/BoundaryStudio.tsx`)을 화면 구성 레퍼런스로 채택하고,
1차 설계서와 어긋나는 지점을 조율했다.

### D5. 분류 용어 — "테마" vs "폴더"
**결정: 화면 용어는 "테마"로 통일.**

- 구조는 설계서의 "폴더(1개) + 태그(복수)"와 동일. 이름만 프로토타입의 "테마"를 쓴다.
- 내부 데이터 필드명은 자유(theme/folder 어느 쪽이든)지만 UI 노출 문구는 "테마".
- **근거**: 프로토타입 UI에 이미 자연스럽게 녹아 있고 더 친근하다.

### D6. 메모 구조 — 단일 vs 다중
**결정: UI는 단일 요약 메모로 시작, 데이터 모델은 처음부터 다중 `Note[]`.**

- 화면은 장소당 메모 1칸(프로토타입) + 지도 노트로 시작.
- DB는 `Note`를 별도 테이블로 두어 장소당 여러 개, `topic` 포함.
- 2단계 AI 관리에서 "주제별 메모 분리" 기능을 붙일 때 다중 메모 UI로 확장.
- **근거**: 설계서 7장의 다중 주제 메모는 핵심 기능이지만, 지금 UI까지 다 만들면 MVP가 무거워진다.
  모델만 미리 다중으로 잡아 두면 나중에 UI만 확장하면 된다.

### D7. 지도·검색 스택
**결정: 하이브리드.**

- **렌더링**: MapLibre GL + OpenFreeMap (Positron/Bright, API 키 불필요, 무료) — 프로토타입 유지.
- **장소 검색·자동완성·상세·Place ID·지오코딩**: Google Places API (종량제, 검색 시에만 호출).
- **장소·경로 열기**: 키 없는 Google Maps URL.
- **근거**: OpenFreeMap엔 장소 검색·Place ID가 없다. 설계서 데이터 모델은 Google Place ID
  기반 중복제거가 뿌리. 렌더링은 무료로 두고 검색만 Google을 쓰면 예쁜 프로토타입 화면을
  유지하면서 설계서의 검색·중복제거를 살릴 수 있다.
- **비용 주의**: Google Cloud 결제 계정과 API 키 발급 필요. Places 호출은 검색 액션에만 발생.
- **대안(보류)**: 전부 무료 OSS(Nominatim/Photon/OSRM). 비용 0이지만 Place ID·Takeout
  매칭이 OSM 기반으로 바뀐다. 필요 시 재논의.

### D8. 백엔드·호스팅
**결정: Cloudflare Workers + D1(SQLite) + Drizzle ORM.**

- 인증은 Google OAuth (Auth.js 호환 계층).
- **근거**: 프로토타입이 이미 Cloudflare/Workers/Drizzle로 스캐폴딩됨(D1 스키마는 비어 있음).
  거리 계산을 클라이언트 haversine으로 하므로 PostGIS가 필수는 아니다. 개인 MVP엔 D1이
  운영·비용이 가볍다.
- **설계서와 차이**: 설계서 권장은 Next.js + PostgreSQL + PostGIS. 프로토타입 자산 재사용과
  운영 단순성을 위해 Cloudflare 경로를 택했다.

## 라운드 3 — AI 대화·승인 인터페이스 (2026-07-23)

상세 설계는 [06-AI승인인터페이스.md](./06-AI승인인터페이스.md).

### D9. AI 인터랙션 모델
**결정: 단발 명령형.** 요청 → 제안 → 승인/거절의 단발 흐름, 각 요청·제안을 개별 레코드로 저장.
대화형 채팅은 이후 확장. **근거**: MVP 복잡도 최소화, 프로토타입 흐름 계승.

### D10. 승인 단위
**결정: 항목별 체크 + 일괄 액션** (`전체 승인 / 선택 승인 / 항목별 수정 / 거절`).
프로토타입 후보 체크박스를 모든 변경유형으로 일반화.

### D11. 변경유형별 표시
**결정: 추가형(후보 카드·점선 핀) / 수정형(이전→이후 하이라이트, 원문 보존) / 삭제형(대상·결과 명시).**

### D12. 표시 위치
**결정: 우측 인스펙터 "AI 제안" 컨텍스트 + 대기 제안 요약.** 지도엔 점선 핀 미리보기.

### D13. 되돌리기
**결정: 반영 직후 실행취소 토스트 + `approval_history` 기반 되돌리기(`reversible`).**
모든 AI 변경은 요청·제안·승인여부·실제반영·시각·되돌리기가능을 기록.

## 라운드 4 — 장소 검색·다중메모·방문계획·인증·AI에이전트 (2026-07-23)

사용자가 "추천대로 쭉 진행"에 동의하여 남은 설계 영역을 추천안대로 확정.
상세: [07-장소검색](./07-장소검색.md) · [08-다중메모](./08-다중메모.md) ·
[09-방문계획](./09-방문계획.md) · [10-인증계정](./10-인증계정.md) · [11-AI에이전트](./11-AI에이전트.md).

### D14. 장소 검색
- Places API (New), 키 서버 전용 + 필드 마스크. 자동완성+텍스트 검색(주변은 선택).
- 활성 바운더리로 `locationBias`(소프트). Places New → `place` 필드 매핑 확정.
- **중복 판정**: ① placeId 일치 → Place 재사용/기존 이동 ② 무ID → 좌표30m+이름유사 → 승인 병합.
  DB `place.googlePlaceId` unique + `bookmark(userId,placeId)` unique.
- 비용 통제: sessionToken, 필드 마스크, Place 상세 캐시. Maps URL(키 불필요)로 열기/경로.

### D15. 다중 메모 UI
- MVP 단일 대표 메모(`topic=null` note 1개) → 2단계에서 주제별 다중 메모 UI 확장.
- AI 정리는 원문 보존(`aiOrganizedContent`/후보 note), 승인 후 반영. 이미지 첨부는 MVP 제외.

### D16. 방문 계획 (4단계)
- 최근접 휴리스틱 + 운영시간 제약으로 순서 초안(드래그 재정렬).
- 이동시간 MVP는 haversine×속도 추정, 정밀은 Routes API 옵션. 실제 내비는 Maps URL 위임.
- 체류시간 입력/카테고리 기본값. 타임라인 출력. 저장은 승인 필수.

### D17. 인증·계정
- Google OAuth 2.0(Auth.js 호환), 스코프 최소(openid/email/profile).
- `sub` 기준 user 식별·생성. 무상태 JWT httpOnly 쿠키 세션.
- 모든 데이터 userId 스코프, 공유 없음. Places/Takeout은 사용자 OAuth 스코프 불필요.

### D18. AI 에이전트 구성
- 도구 호출(search_places/find_bookmarks/organize_notes/detect_duplicates/plan_visit 등).
- 산출은 구조화 `proposedChanges`(op/target/before/after/근거)만 → 승인 프레임 반영.
- 읽기 도구는 승인 불필요. 활동 검색 에이전트 연계(3단계). AI 제공자는 D8 후속으로 미확정.
